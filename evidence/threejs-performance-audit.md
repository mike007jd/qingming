# Three.js 修复与复核记录

2026-09-12 · Apple M2 Max / Chrome / ANGLE Metal。本文取代先前 T0–T9 完成与收益陈述；原始记录保留在备份中。[首次审计](../output/playwright/codex-audit-2026-09-12T04-19-39-565Z/audit.md)列出的功能与采集器问题已修复，未通过画质门槛的实验已回退。既有 LOD 的严格 A/B 门槛仍未闭合，未宣称整体提速目标达成。

## 修复结果

- 船体查询改用本地 Three.js r179 的原生异步回读，按船 ID 关联五个采样点，限制一个逻辑批次在途。同步预热、暂停、cinema、导出、录像与过期刷新提供即时结果；迟到结果不能覆盖 reset 或新的同步结果，回读错误显式抛出。
- 每批只缓存当前船位；普通世界坐标查询随水场版本失效。最多容忍 0.25 秒模拟时间的延迟，再同步刷新。
- 阴影与倒影完成后清除脏标记。普通 auto 动画在镜头/设置不变时隔帧刷新，实际省去对应批处理与通道；镜头、设置变化立即刷新。暂停入口同样尊重显式脏标记，防止松开拖拽后失效状态滞留。
- 清除已回退 MRT 的参数、着色器诊断残留和矛盾测试；描边仍使用独立法线/深度通道。
- Resolution 控件可见且可用；cinema 保持原生 DPR。相同质量档不重复失效，暂停时分辨率变更会重绘。
- 静态画质比较与实际运动探针分开。每侧记录对应帧的 draw/triangle 计数，使用独立原始通道计时；报告和截图使用时间戳。旧 `?perf=1` 入口复用新的比较器。
- 删除将未计入墙钟时间称为 CPU 占比的归因。六段之外还包含水场 GPU 更新与回读；静态样本也不能证明异步或隔帧路径的提速。

原生回读依据已核对的[本地同版本 r179 源码](https://github.com/mrdoob/three.js/blob/r179/src/renderers/WebGLRenderer.js)及 [WebGLRenderer 文档](https://threejs.org/docs/pages/WebGLRenderer.html)。调用后立即解除像素打包缓冲绑定，保持同时存在的同步读回正确；未引入新依赖。

## 画质与保留决策

对照修复前源码快照，在 1280×720、三画风、镜头 1/3/8、auto/cinema 共 18 组上比较：[原始数值](quality/repair-visual.json)。最大输出 RMSE 为 **0.048967 / 255**，最大 over8 为 **0.0000013564**。原材质六组输出逐字节一致；cinema 的法线、倒影和阴影源一致。两种画卷风格的折射源与最终输出仍有少量 MSAA 差异，因此不声称 cinema 全部缓冲逐字节一致。

PCF 单独切换在镜头 8 的 RMSE 为 0.742；阴影投影量化单独启用在镜头 3/8 为 0.777 / 0.902，超过原始画质门槛。两者均回退，保留原有 PCFSoft 与连续投影；[实验数据](quality/repair-shadow-variants.json)。MRT 和人物激进 LOD 实验同样维持回退状态。

## 实际运动验证

[quality 报告](quality/repair-quality.json)的 motion 阶段开启正常动画，不设置 captureSize、recording、exporting 或固定时间。两帧预热后，每镜头测 16 帧：

| 镜头 | 阴影/倒影刷新 | 同步船体回读 | 异步批次 | 缓存峰值 | 帧中位 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 8 / 16 | 0 | 9 | 60 | 127.9 ms |
| 3 | 8 / 16 | 0 | 9 | 60 | 92.5 ms |
| 8 | 8 / 16 | 0 | 9 | 60 | 60.4 ms |

三组动态行为检查通过。以上帧时间是当前运行样本，不是受控的修复前后收益；撤回先前“约 23% 漫游提速”和“GPU 分段证明 CPU 主导”的结论。追舟持续改变相机时按保守规则每帧更新来源。

静态 cinema/auto 比较仍采用 RMSE ≤ 0.6、over8 ≤ 0.002，结果为 **3/9 通过、6/9 失败**。Light Color 三镜头 RMSE 为 2.685 / 1.489 / 0.238；其它画风也在镜头 1/3 超限。这是修复前已存在的远景 LOD 差异，报告保留 failed。要达到该阈值，需要另行改变 LOD 的画质/性能取舍；没有放宽阈值或把失败改称通过。

## 追加：修复前后 FPS 对照

应用户询问另做了受控性能对照。基线为 GLM 交付后、Codex 修复前的 `backup/pre-codex-repair-20260912.tar.gz`，对比当前源码；不是 cinema/auto 档位对比，也不是与更早规格基线比较。M2 Max、Chrome 153.0.8010.36、1280×720、DPR 1、Auto、Light Color。动画与水场持续推进，追舟项持续移动相机；不设置导出、录制或固定时间标记。

每版每场景 8 帧预热、32 帧测量，按“旧→新→新→旧”两轮取合并结果。FPS = 完成帧数 / 总墙钟时间，包含 RAF 等待，以 gl.finish 确认 GPU 完成。主循环由测量脚本驱动，不包含日常 HUD 更新和视频编码开销。

| 场景 | 修复前 FPS | 当前 FPS | FPS 提升 | 帧时间下降 |
| --- | ---: | ---: | ---: | ---: |
| 全景 | 4.4 | 6.7 | +54% | 35% |
| 桥下 | 5.0 | 9.2 | +86% | 46% |
| 街景 | 5.6 | 12.1 | +116% | 54% |
| 追舟 | 4.0 | 7.4 | +86% | 46% |

四场景按相同完成帧数合并为 4.66→8.45 fps，即约 +81%（1.81 倍）；各场景本轮 FPS 增加约 54%–116%，对应帧时间减少约 35%–54%；两者不能混为一个百分比。当前版静止镜头的阴影/倒影各 16/32 次刷新，追舟 32/32 次；四场景预热后同步船体回读均为零。旧版每 32 帧发生 1741–1920 次同步船体回读，各通道均 32/32 次刷新。

这是本机本轮的渲染吞吐量，不是所有设备或分辨率的保证。两轮存在波动（例如当前桥下 8.35–10.33 fps）；结果不用于宣称原规格所有画质/性能门槛已达成。全部测量帧的 GL 错误为零；浏览器日志随原始报告保留。
