# 当前卡顿原因 · 2026-09-12

**正常页面确实偏慢，瓶颈集中在沉重的场景绘制，以及同时存在的主线程工作和 GPU 同步等待。上一轮消除了明确回归，但没有让场景达到流畅运行的预算。**

## 正常应用循环

独立有界面 Chrome，Apple M2 Max / ANGLE Metal，1280×720，DPR 1，Auto，Light Color，正常应用 RAF、动画与生态持续运行。每项预热约 2.2 秒、测量 8 秒，测量帧没有 `gl.finish`、`readPixels` 或 GPU profiler。应用渲染调用计数与实际呈现到屏幕的帧数并非同一指标；这里报告应用循环的帧率。

| 场景 | 应用帧率 | render 调用平均墙钟时间 |
| --- | ---: | ---: |
| 全景 | 6.85 fps | 110.5 ms |
| 桥下 | 8.77 fps | 86.8 ms |
| 街景 | 12.89 fps | 60.6 ms |
| 追舟 | 9.17 fps | 85.4 ms |

全景在较后时刻重复为 5.40 fps / 138.3 ms，说明实际运动场景与系统状态存在波动。这组正常循环结果与上轮同步完成基准同量级，低帧率不能只归因于测量中的 `gl.finish`。上轮 +81% 是相对有回读放大问题的 GLM 交付快照，不代表达到了流畅目标。

## 成本来源与证伪结果

1. **场景反复提交大量几何和材质。** 正常全景平均每应用帧约 4422 次绘制、4234 万个提交三角形；包含完整阴影/倒影刷新的静态帧约 6133 次绘制、5912 万三角形。主画面、阴影、倒影和描边法线通道会多次提交同一场景。独立描边还保留一遍场景几何；4×MSAA、4096 阴影图也仍在使用。
2. **LOD 后仍有大量细节。** 两帧精确 renderer.info 增量统计中，细节 GLB 部分贡献 3065 万三角形和 3162 次绘制，其余城市/人物/水面贡献 5342 万三角形和 5675 次绘制。高位对象包括逐块铺设的路面、城墙、人物、LOD2 树叶、瓦片和高密度水面。细节并不是唯一成本。
3. **回读仍能阻塞主线程，但不是当前 FPS 的唯一限制。** 8 秒 CPU 采样中，28.4% 时间落在 `getParameter`，24.5% 落在 `getBufferSubData`。调用栈指向本地 r179 `textureTypeReadable → readRenderTargetPixels[Async]` 与异步缓冲读取；不能把这些等待比例直接解释成“去掉即可提升 53% FPS”。此外，`contacts`、`stepPeople`、`pose` 分别约占采样时间的 7.9%、3.2%、2.5%，碰撞/生态/骨骼也有成本。采样比例是主线程记录时间，不是 CPU/GPU 利用率。

对照“正常→缓存浮点能力检查→冻结船体样本→冻结船体样本→缓存能力检查→正常”，合并两轮：

| 临时诊断条件 | FPS | render 墙钟时间 |
| --- | ---: | ---: |
| 正常 | 7.21 | 103.09 ms |
| 跳过已知 FloatType 的重复能力查询 | 7.43 | 86.63 ms |
| 用已有船体样本替代 GPU 回读 | 7.59 | 66.48 ms |

移除回读让主线程更快返回，但整体 FPS 只升约 5%，图形管线剩余工作继续限制吞吐。单项探针中，停水场模拟约 6.89 fps，关描边约 7.28 fps，降低渲染尺寸至 640×360 约 7.17 fps；均没有单独恢复流畅。尺寸探针也改变了投影 LOD 条件，不能作为纯填充率实验。隐藏细节网格两次分别为 9.44 和 9.16 fps，正常对照约 6.7–6.9 fps；既表明细节层昂贵，也表明仅处理这一层仍不够。关闭人物的单次探针反而更慢，不能据此认定人物免费或关闭人物必然退化。

## GPU 计时的适用范围

另用 `EXT_disjoint_timer_query_webgl2` 包围 24 个应用渲染调用，测量阶段不读取计时结果，停止应用循环后再收集。GL error=0、disjoint=false。正常 / 冻结取样 / 隐藏细节的 GPU elapsed 均值分别约 237.6 / 225.8 / 50.8 ms。

这些计数与应用帧间隔不是可直接相加的账本，正常均值甚至大于同期约 150 ms 的应用帧间隔；因此不据此精确拆分 CPU/GPU 占比，也不用倒数宣称呈现 FPS。隐藏细节时 elapsed 大幅下降，与两次应用 FPS 改善共同支持图形绘制负载较重的判断。

## 下一轮应解决什么

以 30 fps 的 33.3 ms/帧为目标，先为远景瓦片、树木、角色、路面与材质划定实际预算，再处理对应的 LOD/实例化/合批，以及阴影、倒影、描边的对象集合与刷新成本。碰撞查询和人物更新按 CPU profile 跟进。回读能力检查可继续减轻主线程等待，但它单独无法填平当前帧时间缺口。

这轮只诊断：探针都在独立浏览器中临时修改运行状态，没有把冻结水面、隐藏物体或降低分辨率写入产品。
